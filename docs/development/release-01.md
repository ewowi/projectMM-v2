# Release 1 — Restart to Parity

> **Theme:** Bring v2 to parity with v1's first-boot pipeline — effect → blend → driver → preview, served over HTTP / WS with WiFi-STA, persisted to LittleFS, OTA-updatable, NTP-synced, ArtNet-capable — over six sprints. The decision to restart from v1 is documented in v1's [Release 9](https://ewowi.github.io/projectMM/development/release-09/). The main driver is **frugality** (frugal in code, in CPU cycles, in resources); the [guardrails framework](guardrails.md) lands in Sprint 1 before any module exists, and the [anti-drift rules](anti-drift.md) constrain every sprint that follows.

---

## Release Overview

### What Release 1 delivers

A v2 codebase that runs the same first-boot pipeline as v1, implemented as modules over a small core that fits in one head. The core is `Module` + `ModuleManager` + `Scheduler` + a minimal `Pal`; networking, OTA, NTP, persistence, the HTTP / WS server, and the entire lighting domain (`RGB`, `pixelBuf`, effects, layers, layouts, modifiers) are modules. The deploy pipeline is three scripts: build, flash, test. v2's first user is lights, but lights live in `modules/lights/` and depend on the core, not the other way around.

### Frugality targets (CI-enforced)

| Surface | Target |
|---------|--------|
| Core (Module + Manager + Scheduler) | ≤ 300 LOC |
| Pal | ≤ 200 LOC |
| Per module (light domain) | ≤ 200 LOC |
| Per module (networking, OTA) | ≤ 300 LOC |
| Tests after Sprint 2 | ≤ 5 files |
| Deploy scripts after Sprint 1 | 3 (build, flash, test) |

Overshoot fails CI. Bumping a target requires an explicit line in this release plan signed off by the maintainer.

### Concurrency model (fixed at Sprint 1)

Arbitrary DAG topology, SPSC lock-free ring buffer per edge, depth 2 by default. The linear pipeline (effect → blend → driver) and v1's double-buffering are special cases. Depth >2 enables backpressure pipelining where memory allows.

### Recurring evaluation cadence

Release 5 is the first recurring evaluation release (per the [anti-drift schedule](anti-drift.md): every fifth release is a no-feature evaluation). It is scheduled here, in Release 1 Sprint 1, not at the end of Release 4.

| Sprint | Goal | Frugality target |

## Sprint 1 — Guardrails and skeleton {#sprint-1}

> **Scope:** Land the guardrails framework (pre-commit hooks, CI gates, structural rules) before any module exists. Write the empty `Module`, `ModuleManager`, `Scheduler`, and `Pal` skeletons such that `loop()`, `loop20ms()`, `loop1s()`, and `loop10s()` are first-class scheduler concerns from commit 1, not afterthoughts. CI green on PC and ESP32.

The framework is the load-bearing deliverable. Without it, the same drift that produced v1 reaches v2 by Sprint 4. The [guardrails outline](guardrails.md) is the spec; the first commit of this sprint is its implementation. `loop20ms()` is new in v2 (v1 had only `runLoop1s` via timing windows); the scheduler maintains four pinned task ranks per core (hot, 20 ms, 1 s, 10 s) and modules opt into each by overriding the corresponding method. Empty overrides cost nothing.

The drift-metrics dashboard from the anti-drift rules lands as a status doc generated by CI on every push.

### Definition of Done

- [ ] `.gitignore`, `CMakeLists.txt`, `platformio.ini` in place
- [ ] Pre-commit hooks installed and green: clang-format, ruff, raw-GPIO ban, hot-path allocation ban, hot-path blocking-call ban
- [ ] CI workflow green on PC (macOS + Linux + Windows) and ESP32 (esp32dev + esp32s3_n16r8)
- [ ] CI gates enforced: LOC budget, footprint baseline, test-count baseline, doc growth budget, structural-file gate
- [ ] `Module` base class declares `setup` / `loop` / `loop20ms` / `loop1s` / `loop10s` / `teardown` (empty defaults)
- [ ] `Scheduler` runs a no-op tick on both cores; pinned-task ranks wired
- [ ] `ModuleManager` adds / removes a no-op module via API
- [ ] `Pal` skeleton has timing only (everything else lands in Sprint 3)
- [ ] Core total ≤ 300 LOC; verified by CI
- [ ] Drift-metrics status doc published by CI
- [ ] Release 5 evaluation sprint scheduled in this release plan

## Sprint 2 — First module and test pyramid {#sprint-2}

> **Scope:** Add `HelloModule` (registers one control, logs a line in `setup()`, increments a counter in `loop20ms`). Wire the four-tier test pyramid: host unit (doctest, single binary), on-target unit (Unity or doctest on ESP32), integration (REST against in-process server), HIL (live device probe). Each tier covers exactly one kind of bug; no overlap.

### Definition of Done

- [ ] `HelloModule` ships with one control and a counter, both visible over REST
- [ ] Host unit tests run on PC for every module
- [ ] On-target unit tests run on ESP32 for the same modules where platform behaviour differs
- [ ] Integration tests run against the in-process server, not over the network
- [ ] HIL probe verifies serial output on a connected device (skipped in CI without hardware)
- [ ] Test count baseline locked at sprint close; bump rule enforced

## Sprint 3 — Pal-minimum {#sprint-3}

> **Scope:** Implement `Pal` for timing, GPIO (via typed board config), filesystem basics, RTOS task and semaphore primitives, and heap query. Nothing else. WiFi, Ethernet, UDP, OTA, NTP, system-info dumps, and OTA partition queries do **not** live in `Pal`.

### Definition of Done

- [ ] Pal total ≤ 200 LOC across all platforms
- [ ] PC and ESP32 builds green
- [ ] Typed board config (`board/<env>.yaml` → `Pins.hpp` codegen) compiles for esp32dev and esp32s3_n16r8
- [ ] No `pinMode(<integer>)` or `digitalWrite(<integer>)` anywhere in the codebase (enforced by pre-commit)

---

## Sprint 4 — Light domain {#sprint-4}

> **Scope:** Port the light pipeline as modules. One producer (effect), one consumer (preview driver), SPSC ring buffer between them at depth 2. `RGB`, `pixelBuf`, and the producer / consumer base classes live in `modules/lights/`, not in core. The DAG declaration API (`scheduler.connect(producer, consumer)`) is exercised by this sprint.

### Definition of Done

- [ ] `EffectBase` and `DriverBase` in `modules/lights/`
- [ ] At least one effect (`SineEffect` or similar) producing a frame
- [ ] At least one preview driver consuming it and exposing pixels over WS
- [ ] SPSC ring buffer primitive in core, depth 2, ESP32 + PC
- [ ] PreviewModule frame rate matches v1 on the same hardware
- [ ] Per-module footprint ≤ 200 LOC

---

## Sprint 5 — Networking modules {#sprint-5}

> **Scope:** WiFi-STA, HTTP server, WebSocket server, REST API. All as modules. The HTTP / WS server uses the same wire format as v1 so the v1 frontend can connect unchanged during the transition.

### Definition of Done

- [ ] `WifiStaModule` connects on boot using credentials from state
- [ ] `HttpServerModule` serves the frontend bundle
- [ ] `WebSocketModule` pushes schema and state with the v1 wire format
- [ ] REST endpoints `/api/modules`, `/api/system`, `/api/log` parity with v1
- [ ] v1 frontend connects to v2 device unchanged
- [ ] Per-module footprint ≤ 300 LOC

---

## Sprint 6 — Parity sprint {#sprint-6}

> **Scope:** ArtNet (in + out), OTA firmware update, NTP wall-clock, LittleFS state persistence. Sprint closes when the v1 first-boot pipeline runs identically on v2 hardware.

### Definition of Done

- [ ] `ArtNetInModule`, `ArtNetOutModule` ship, wired by `autoWireKeys()`
- [ ] `FirmwareUpdateModule` accepts file upload and GitHub-release flashing
- [ ] `NtpModule` syncs and exposes `local_time`
- [ ] State persistence via LittleFS modules
- [ ] First-boot pipeline runs identically on v2 hardware (visual + metrics parity check against v1)
- [ ] v1 tagged `v1.8.x-legacy`; this repo renamed from `projectMM-v2` to `projectMM`; v2 tagged `v2.0.0`
